## Why

When a model's layers span Macs, every token pays a network round trip per hop. Over the internet that
round trip, not the GPUs, sets the speed. Each change here has to be measured, not guessed.

## What is in place

- **Speculative decoding** (`generation/speculative.py`). A draft model on the head Mac proposes `k`
  tokens, and the pool checks them all in one pass. Verification samples the big model at each position
  and keeps a proposal only if it matches, so the output is what the big model would have written. It
  runs only when a turn spans Macs and `DOTS_DRAFT_MODEL` names a draft with the same tokenizer.
  Rejected tokens are trimmed from every cache in the chain (`trim_cache`).
- **Per-pass timing** (`distributed/chain_timing.py`). The head times its own layers and each hop's round
  trip, and the peer reports its compute. The hub logs it on every turn's "done" line, together with how
  many draft tokens were kept.
- **Draft display**. The draft's proposal streams to the app as a `dots` draft event and shows greyed
  out until the pool confirms it.

## Measurements

The simulated two-Mac pool (`scripts/bench_decode.py`): Qwen2.5 1.5B split in two with an injected round
trip, Qwen2.5 0.5B as the draft, four draft tokens.

| Round trip | One token at a time | Speculative | Same output |
|---|---|---|---|
| 0 ms | 1.00× | 0.60× | yes |
| 25 ms | 1.00× | 1.12× | yes |
| 50 ms | 1.00× | 1.35× | yes |
| 100 ms | 1.00× | 1.76× | yes |

At six draft tokens the output drifted, from batched floating-point numerics; four is the default.

Two real workers on one Mac, Qwen2.5 1.5B at temperature 0. The output was identical with and without the
draft, and the draft kept 23 of 68 proposals (2.4 tokens a pass). Per pass, without the draft:

| Part | Time |
|---|---|
| Head, 1 layer plus embeddings | 1.1 ms |
| Peer, 27 layers | 15.4 ms |
| Wire and copies, loopback | 3.7 ms |

The ping between the two is 0.7 ms, so about 3 ms of the wire is the message path (framing, QUIC,
asyncio handoffs). Hidden states already go as raw bytes.

## Checked

- **A model that fits stays on one Mac.** With two or three Macs each holding the whole model, a turn runs
  on one of them with no hop, on the asker's own Mac when they have one; a smaller Mac joining stays idle
  (`tests/distributed/test_whole_model_stays_on_one_mac.py`).
- **How a split falls when it must.** For one answer the layers run one after another, so a token costs the
  sum of every Mac's share: balancing the layers buys nothing. What matters is the number of hops and how
  many layers the fastest Macs carry. Today's split follows memory: two equal 10 GB Macs get 8 and 20
  layers, and when one of them is four times faster the split is the same, with the head (which also runs
  the vocabulary-sized output layer) on the slower one. In the real two-worker test above, the 1 and 27
  split was forced by memory: the head also holds the embeddings and its working space.
- **The head goes where it is fast.** The scheduler now counts the head's output layer (vocabulary by
  hidden size, about six decoder layers for Qwen2.5) as work. With equal memory and one Mac four times
  faster, the fast one becomes the head with 16 layers and the slow one takes 12; before, the slow one was
  the head. By the scheduler's own estimate that is about 9% faster a token.

- **A ring, as an option** (`DOTS_CHAIN=ring` on the workers). The head sends a pass to the first peer;
  each peer runs its layers and hands the hidden state to the next; the last sends it home, and a failure
  goes straight to the head. n + 1 legs a pass instead of 2n, so it only pays from two peers up. On one Mac
  with two segments it gave the same words as the star and the same speed within noise (19.9 against
  18.1 ms a pass). Star stays the default until a three-Mac WAN run says otherwise.

- **Sending bytes is ten times cheaper.** The iroh bindings (generated by uniffi) copied every outgoing
  byte into Rust in a Python loop, about 0.17 microseconds a byte. `iroh_net` now swaps in one memory
  copy and checks it gives the same bytes. Round trips on loopback (`scripts/bench_wire.py`):

  | Message | Before | After |
  |---|---|---|
  | ping | 0.55 ms | 0.55 ms |
  | 1 token, 3 KB | 1.64 ms | 0.52 ms |
  | 5 tokens, 15 KB | 5.97 ms | 0.98 ms |
  | 64 tokens, 192 KB | 68.0 ms | 6.9 ms |

  On the live two-worker pool the wire went from 3.8 to 1.7 ms a pass and a 60-token answer from 1.50 to
  1.25 s, with the same words. Prompts gain the most: a 1,000-token prompt's hidden states for a
  1536-wide model are 3 MB, and a round trip of that measured 1,047 ms with the old copy and 111 ms now.

- **Adaptive draft length**, on by default (`DOTS_DRAFT_ADAPTIVE=0` turns it off). After a check that
  threw guesses away the draft guesses fewer (as many as were kept, plus one), and after one that kept
  them all it guesses one more, up to `DOTS_DRAFT_TOKENS`. A check costs more the more it checks, so
  doomed guesses are expensive. Same words either way; on the simulated pool, up to four guesses:

  | Round trip | Fixed | Adaptive |
  |---|---|---|
  | 0 ms | 0.59× | 0.81× |
  | 25 ms | 1.14× | 1.20× |
  | 50 ms | 1.39× | 1.34× |

- **A Metal kernel for checking drafts** (`backends/mlx/small_batch.py`). MLX's 4-bit layers have a fast
  path for one token and a slow one for a few: on Qwen2.5 1.5B a pass of five tokens cost 3.5 times one.
  The kernel reads each packed weight once for every token in the pass, and takes 2 to 5 tokens on large
  layers (past that its registers spill). Whole-model passes, 2 to 5 tokens: 1.33 to 1.65 times faster.
  End to end with adaptive drafting, up to four guesses:

  | Round trip | MLX | With the kernel |
  |---|---|---|
  | 0 ms | 0.78× | 0.85× |
  | 25 ms | 1.19× | 1.26× |
  | 50 ms | 1.36× | 1.47× |

  The check now adds in a different order than one-token decoding, so where two words are all but tied
  the pick can differ: in one of three test answers the text matched for 277 characters, then said "blue
  light" where one-at-a-time said "the shorter blue wavelengths". Both are the big model's choice; neither
  is more right. `DOTS_SMALL_BATCH_KERNEL=0` turns it off.

- **The app shows it.** Ask's Draft ahead toggle sends `X-Dots-Speculate`; the hub keeps each model's
  plain speed per chain length and reports a drafted answer's speedup against it, slower included.
